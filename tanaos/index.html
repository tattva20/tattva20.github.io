Real-time audio operating system · Rust · Raspberry Pi 4

tānaOS

An operating system written from the first instruction up, whose job is to host instruments. Synthesizers and effects each run in a partition of their own, so one that runs late is cut at its time slice instead of taking the music down with it.

Where it stands today

Status, 8 October 2026. Phase 1 (the kernel) and phase 2 (the audio host) are complete and verified on real hardware. Phase 3 (GATTO, the first instrument) is in progress: the first guest already computes its own audio in an isolated, unprivileged partition, and MIDI crosses a real optocoupler into the board. The source is private for now.

What it is, and why it exists

Every music program on a computer hosts plugins the same way: all of them in one process, sharing one deadline. When one plugin takes too long, everything glitches together. That is not a bug in any one plugin; it is the shape of the host.

tānaOS takes a different shape, borrowed from avionics. The ARINC 653 standard partitions an aircraft's computer so that a failing function cannot starve the ones that keep the plane in the air: each partition gets its own memory and its own guaranteed slice of time, and a partition that overruns its slice is cut. Here the partitions are instruments. A synthesizer that overruns is cut at its budget; the rest keep sounding.

It runs on a Raspberry Pi 4: four Cortex-A72 cores at 1.5 GHz. The design is AMP, not SMP — instead of one scheduler spreading work across cores, each core has a known job. Audio at 48 kHz is known before the machine boots, so a core dedicated to it keeps its cache warm and never has to be shared.

The name comes from Sanskrit √tan, "to extend". Tāna is the extended melodic run that elaborates a raga over its fixed frame. The kernel is tan_k — the same root plus K for kernel. The kernel is the warp; the system is what gets woven on it.

The road, phase by phase

The project is split into phases, each with its own written charter and its own finish line. A phase is closed only when every claim on its list has been shown on the board, or recorded as a named limit.

Phase 2 · the host, tānaOS closed · 20 September 2026

Phase 2 turned a kernel into an audio host. Its finish line was written as a test: the phase is done when a synthesizer could be written against it, whether or not one has been. Each capability was first proven in a kernel of its own, then composed into the one that ships.

  • Sound out. I²S to a PCM5102A DAC, fed by DMA through a two-block ring: 32 stereo frames at 48 kHz, a new period every 666.7 µs.
  • A core for audio. The shipped kernel releases a second core and hands it periods straight from the DMA ring's completion interrupt.
  • A budget that cuts. Each period is held against a stated ceiling; a partition that spends past it is cut, not waited for.
  • A console that stopped starving the audio. Printing used to block; a 2 KiB transmit ring took dropped period boundaries from ten to zero.
  • Heard and measured. On 17 September a person heard 750 Hz on the left and 1500 Hz on the right from the shipped kernel, started from its own shell.

Phase 3 · the first instrument, GATTO in progress

GATTO — Generative Audio Tone & Timbre Operator — is the first guest tānaOS is asked to carry. Phase 2 built the host; phase 3 builds a guest, and in doing so finds out what the host got wrong. That is the point of building one.

The first voice is an FM synthesizer, decided on 17 September, and not out of nostalgia. At 1.5 GHz a core has 31,250 cycles per audio sample; a partition is granted half, 15,625. A four-operator FM voice with envelopes costs on the order of sixty. That is hundreds of voices per core before the vector unit is even touched. Compute is not the constraint — architecture and control are, which is exactly what a first guest should exercise. And an FM voice's whole state is tens of bytes, so it lives in the L1 cache, where a sample-playback voice would be reading megabytes from slow memory on every note.

Phase 3 is finished when three stages run on three cores and one of them can be starved without taking the others down. That is the claim the whole design rests on, and it needs at least two guests to be shown.

Measured, not assumed

Every number on this page comes from a run on the board, kept as a transcript in the repository. A few of them changed the design.

The shipped kernel sounds clean (5 October). Its audio was captured electrically through an audio interface and judged against a floor taken from the same chain measuring nothing. This is not a test kernel playing a table: it is the kernel that ships, with six tasks sharing the machine and the guest under its budget.

  • The guest at EL0. Moving the guest out of the kernel's privilege level raised its worst period from 0.23% to 0.34% of the budget. Isolation costs about a tenth of one percent of a period, and it bought a guest that cannot touch anything it was not given.
  • A wait must be a loop. Waiting for a period with a single check missed 5 periods over four runs, because any atomic operation on any core can wake a sleeping core. Rewritten as a loop: 0 late, and the cost fell from about 860 system calls per period to one.
  • The emulator lies kindly. QEMU starts with memory zeroed; the Pi does not, and after a warm reboot it keeps the previous boot's contents. The kernel poisons memory before clearing it, so a broken clear shows up instead of hiding.
  • The firmware under-reports memory. The mailbox says 948 MiB on a 2 GiB board. The kernel reads the device tree instead: the allocator went from 242,495 free frames to 504,630.
  • What the emulator cannot see, the board decides. No emulator models the Pi's spare UARTs, the data cache, or stack-alignment faults. Those are tested on the bench, with a logic analyzer when a loopback cannot tell the difference.

How it is built

  • Stable Rust, nothing underneath. No operating system, no standard library, no crates, no bootloader. The firmware loads the image and jumps to its first byte.
  • Every test is a kernel. Each test file compiles into a standalone kernel and boots in its own emulator, which is what lets a test pass by crashing the machine on purpose.
  • Two hand-offs, two optimisation levels. The gate boots each test as if handed off at EL1 and at EL2, in debug and release — a register bug once showed in debug and hid at -O2.
  • Numbers kept honest by scripts. Line counts, memory footprints and test counts in the documentation are measured on every run; the gate fails when the prose and the measurement disagree.
  • A budget for size. The kernel has a 15,000-line ceiling, and the mutable state has to fit on one printed page.
  • Built with AI assistance, under human judgment. I design, decide and sign off every step; AI widens what one person can reason through and review. The method is documented in the Combined Force series.

What comes next

  • Notes from a real keyboard reaching the guest over the MIDI port, turned into the FM voice's parameters.
  • A second stage fed by the first, and with it the first demonstration that one instrument can be starved while another keeps playing.
  • Deciding GATTO's shape — a chain of stages or independent voices — in writing, before it is built.
  • Opening the source. tānaOS is meant to be Mexican technology for the world: an open alternative in a field of closed DSP platforms.

Not a product yet — a working system, measured on its own hardware, getting its first instrument.
